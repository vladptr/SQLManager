# SQLManager

Локальний візуальний конструктор Oracle SQL для роботи з моделлю РЗО/Т6. Застосунок допомагає зібрати запит через простий український інтерфейс: вибрати джерела, зв’язки, поля, готові показники, фільтри та спосіб отримання результату.

Проєкт працює повністю локально як статичний HTML/CSS/JavaScript-застосунок. Він не підключається до Oracle, не виконує SQL і не передає дані назовні — лише генерує текст запиту.

## Поточний стан

Робоча гілка: `feature/sqlmanager-improvements`.

На цей момент реалізовано:

- майстер побудови запиту з шести кроків;
- каталог таблиць і колонок із простими українськими назвами;
- детермінована побудова `JOIN` як обхід графа таблиць;
- складені умови зв’язку з кількох пар колонок;
- кардинальність `1:1`, `1:N`, `N:1`, `N:M`;
- попередження про можливе розмноження рядків;
- явна помилка для непов’язаного графа замість неявного декартового добутку;
- вибір колонок, агрегатів, сортування та фільтрів;
- готові семантичні показники;
- режими `SELECT`, `CREATE TABLE AS` і `DROP TABLE + CREATE TABLE AS`;
- перевірка Oracle identifier і технічних аліасів для CTAS;
- копіювання SQL і завантаження файлу `.sql`;
- окремий розділ готових SQL-шаблонів;
- автоматичні браузерні тести генератора.
- автоматичне додавання проміжних bridge-таблиць, яких користувач не вибирав вручну;
- джерела ЄРСП, КВЕД і категорій страхувальників;
- opt-in preset актуальних реквізитів страхувальника.

## Як запустити

Найпростіший спосіб у Windows — запустити:

```text
start.bat
```

Або відкрити `index.html` у Google Chrome. Сервер і встановлення залежностей не потрібні.

`start.bat` заново збирає `SQLManager-portable.html` з актуальних файлів у папках `data`, `js` і `css`, а потім відкриває його: спочатку в Google Chrome, потім у Microsoft Edge і лише після цього у браузері за замовчуванням. Це не дає випадково запустити застарілу переносну копію після оновлення проєкту. Якщо копіюєте тільки один HTML-файл, спочатку запустіть `start.bat`, а вже потім копіюйте щойно оновлений `SQLManager-portable.html`.

Переносну версію також можна оновити вручну:

```powershell
powershell -ExecutionPolicy Bypass -File build-portable.ps1
```

Кнопка **«Зберегти пресет»** біля SQL зберігає поточну конфігурацію конструктора у локальному сховищі браузера. Завантаження й видалення доступні на кроці **«Шаблони»** в секції **«Мої пресети конструктора»**. Збережені пресети не містять результатів Oracle і не передаються мережею; вони прив’язані до конкретного браузера та комп’ютера.

## Фізичний каталог із DDL

`tools/import-ddl.ps1` читає `rzo_schema_4.sql`–`rzo_schema_7.sql` на етапі збірки й детерміновано створює `data/physical-schema.generated.js`. DDL-файли не завантажуються браузером. Згенеровані таблиці, колонки, PK, UNIQUE, CHECK і FK доповнюють ручну семантичну модель; українські назви, зернистість, попередження, presets і дефолтні маршрути з `data/schema.js` мають пріоритет.

Фізичні FK імпортуються як недефолтні ребра з великою вагою. Тому короткий FK не змінює перевірені бізнес-маршрути `current_insurer_profile`. Складений FK є одним ребром із кількома `conditions`. Посилання на схеми без DDL мають ознаку `unresolvedExternal`.

- `rzo_schema_4.sql`: 112 таблиць, 1 752 колонки, 89 PK, 226 FK;
- `rzo_schema_5.sql`: 88 таблиць, 809 колонок, 81 PK, 135 FK;
- `rzo_schema_6.sql`: 59 таблиць, 576 колонок, 56 PK, 61 FK (`IKIS_NDI` і частина `IKIS_PERSON`);
- `rzo_schema_7.sql`: 30 таблиць, 344 колонки, 29 PK, 102 FK (КАТОТТГ, категорії ЗО та персональні довідники);
- разом: 289 таблиць, 3 481 колонка, 255 PK, 524 оголошення FK; після дедуплікації повторних constraint — 499 фізичних ребер графа.

`GLOBAL TEMPORARY TABLE TMP_IDS` не входить у контрольні числа постійних `CREATE TABLE`.

## Зарплатні показники та зернистість

Універсальний `AVG` недоступний для сум зарплати. Зарплатні показники спочатку формують `person_employer_month` за ключем `year, aped46_mnth, kod_zo, slb_im/edrpou`. Для аналізу унікальних людей CTE `person_month` підсумовує роботодавців за ключем `year, aped46_mnth, kod_zo`.

Один звіт може одночасно містити фонд оплати, внески ЄСВ, кількість осіб/страхувальників/рядків і один коректно визначений показник середньої зарплати. Для розрізів за КВЕД або підприємством використовується зерно `person_employer_month`; агрегація T6 виконується до приєднання довідників.

- `person_month`: одна людина в місяці є однією одиницею; зарплата всіх роботодавців підсумовується.
- `person_employer_month`: кожне поєднання людини й страхувальника в місяці є окремою одиницею зайнятості; цей рівень потрібний для підприємств і КВЕД.

Формули:

- `avg_salary_month`: `SUM(salary_month) / NULLIF(COUNT(*), 0)`, групування за роком і місяцем;
- `avg_monthly_salary_period`: зважена формула на всіх людино-місяцях періоду;
- `median_monthly_salary_period`: Oracle `MEDIAN(salary_month)` на місячних значеннях після приведення до зерна `person_month` або `person_employer_month`;
- `avg_monthly_salary_year`: формула на людино-місяцях із групуванням за роком;
- `avg_annual_salary`: `12 * SUM(salary_month) / NULLIF(COUNT(*), 0)`, лише для місяців 1–12 повного календарного року;
- `avg_annual_income_per_person`: після `person_year` — `SUM(salary_year) / NULLIF(COUNT(*), 0)`.

Режим `current` використовує підтверджені статуси `IM_ST`, `IH_ST_ACTUAL` та `IV_TP`. DDL не доводить, що вони завжди залишають рівно один головний КВЕД на страхувальника, тому порядок для штучної дедуплікації не вигадується. Перед використанням у продуктивній аналітиці потрібно виконати [контроль дублів](docs/control-current-kved-duplicates.sql) і погодити бізнес-правило, якщо він повертає рядки.

Правило `reported` включає місячну одиницю, якщо у T6 є запис. Правило `positive_salary` застосовує `salary_month > 0` тільки після місячного підсумовування, тому сторнування не відкидається завчасно. Для КВЕД та історичних довідників агрегація відбувається до JOIN. Підтримуються лише `current` (актуальний стан) і явно підтверджений `all_history` із попередженням про fanout. Режим станом на дату ще не реалізований. `latestPersonOnly` є окремою функцією картки особи, а не semantic mode. `DISTINCT` для маскування розмноження не застосовується.

Контрольний приклад: A має 10 000 у січні й 20 000 у лютому, B — 30 000 у січні. Січень: 20 000; лютий: 20 000; період: 60 000 / 3 людино-місяці = 20 000; фактичний дохід за період на унікальну особу: 60 000 / 2 = 30 000.

## Семантична модель

`data/schema.js` — це вже не просто список колонок. У моделі зберігаються:

- фізична назва й псевдонім таблиці;
- зрозуміла назва джерела;
- зернистість даних (`grain`);
- колонки та перевірені типи;
- зв’язки між таблицями;
- складені умови `conditions: [{ leftCol, rightCol }]`;
- тип `JOIN` і кардинальність;
- спеціальні CTE для безпечного приєднання;
- системні фільтри сирої звітності;
- готові аналітичні показники.

Порядок, у якому користувач вибрав таблиці, не впливає на SQL. Генератор вибирає стабільний корінь графа і додає кожне джерело у `FROM/JOIN` рівно один раз.

Користувачеві не потрібно вручну вибирати проміжні таблиці. Наприклад, для `sm_packlabel → pinsur_ankt_a` автоматично додаються `pinsur_main` і `pinsur_chng_doc`. Для робочої T6 та довідника КВЕД маршрут проходить через `pinsur_main → pinsur_chng_doc → pinsur_kved_hst → pinsur_kved`. Поля bridge-таблиць не потрапляють у `SELECT`, якщо користувач їх явно не обрав.

Якщо всі вибрані таблиці неможливо зв’язати, SQL не генерується. Користувач отримує повідомлення з назвами джерел, для яких немає шляху.

## Реалізовані зв’язки

Основні зв’язки, які вже описані в моделі:

| Джерела | Умова | Тип | Кардинальність |
|---|---|---|---|
| `t6_2026_edrpou → insured_person_info` | `kod_zo = numident` | `LEFT` | `N:1` |
| `insured_person → insured_person_info` | `ip_id = ip_id` | `INNER` | `1:N` |
| `sm_packlabel → sm_ape4_6data` | пакет | `INNER` | `1:N` |
| `sm_packlabel → sm_ape4_5data` | пакет | `INNER` | `1:N` |
| `sm_ape4_6data → sm_ape4_5data` | пакет + РНОКПП | `LEFT` | `N:1` після агрегації |
| `sm_packlabel → mrdorg` | орган обліку | `INNER` | `N:1` |
| `sm_packlabel → pinsur_main` | страхувальник | `INNER` | `N:1` |
| `pinsur_main → pinsur_chng_doc` | документ змін | `INNER` | `1:1` |
| `pinsur_chng_doc → pinsur_ankt_a` | анкета | `INNER` | `N:1` |
| `pinsur_chng_doc → pinsur_ankt_b` | анкета Б | `INNER` | `N:1` |
| `pinsur_chng_doc → pinsur_ankt_c` | територіальна анкета | `LEFT` | `N:0..1` |
| `pinsur_ankt_a → nsi_insurercat` | категорія страхувальника | `INNER` | `N:1` |
| `pinsur_chng_doc → pinsur_kved_hst` | версія КВЕД документа | `INNER` | `N:1` |
| `pinsur_kved_hst → pinsur_kved` | записи КВЕД версії | `INNER` | `1:N` |
| `pinsur_kved → nsi_kved` | код КВЕД | `INNER` | `N:1` |

Для `pinsur_main → pinsur_chng_doc` існують два різні маршрути. Default-маршрут історії документів використовує `im_id = ih_im` (`1:N`). Вказівник `im_ih = ih_id` (`1:1`) збережено окремо, але він не використовується автоматично до підтвердження семантики в Oracle.

Preset «Актуальні реквізити та КВЕД страхувальника» додає лише за явним вибором:

```sql
im.im_st IN ('A', 'L')
AND ih.ih_st_actual = 'A'
AND kv.iv_tp = 'Y'
```

Без preset ці умови не застосовуються, тому історичний аналіз залишається доступним. Маршрут `1:N → 1:N` до КВЕД супроводжується попередженням про можливе розмноження сум T6.

### Картка особи

Для `t6_2026_edrpou → insured_person_info` доступні два способи зіставлення:

1. Точний збіг `t6.kod_zo = ipi.numident`.
2. РНОКПП або паспортний ключ:
   - `TRIM(numident)`;
   - `БК` + серія у верхньому регістрі + номер паспорта;
   - `П` + номер паспорта.

За замовчуванням конструктор приєднує всі записи `insured_person_info`. Фільтр «Лише остання картка особи за датою зміни» явно вмикає CTE з `ROW_NUMBER()` за `modify_dt DESC, ip_id DESC`. Це правило однаково застосовується до зв’язків картки особи з робочою T6 та APE 4-5.

### Людина, роботодавець і кадрові події

Якщо потрібні місце роботи, прийняття, звільнення або посада конкретної людини, слід вибрати картку особи, `sm_ape4_5data` і страхувальника. Конструктор використовує семантичний маршрут:

```text
insured_person_info
→ sm_ape4_5data (за РНОКПП)
→ sm_packlabel (за номером пакета)
→ pinsur_main (за внутрішнім ID страхувальника)
```

APE 4-5 містить дати прийняття і звільнення, професійну назву роботи, код класифікатора професій, посаду, документ-підставу, ознаки сумісництва та переведення. Одна людина може мати декілька кадрових подій або посад, тому генератор показує попередження про можливе розмноження рядків.

У DDL також підтверджено FK `APED45_PEL → PERSON_ESV_LINK.PEL_ID`, але таблицю `PERSON_ESV_LINK` не додано до каталогу без її повного DDL.

Для зв’язку робочої `t6_2026_edrpou` безпосередньо з APE 4-5 картка особи не потрібна. Доступні чотири варіанти: усі посади у страхувальника; посади лише за той самий рік і місяць; остання відома посада; остання посада станом на місяць рядка T6. Останні два режими використовують `ROW_NUMBER()` з пріоритетом `APED45_DATE_HIRE DESC`, потім звітного періоду пакета і номера рядка. Режим «станом на місяць» не враховує кадрові події, датовані пізніше останнього дня місяця T6, тому може повернути попередню посаду до переведення. `SLB_IM`, рік і місяць для APE 4-5 беруться з `SM_PACKLABEL` усередині технічного CTE. Цей маршрут активний лише тоді, коли користувач явно вибрав обидва джерела, і не використовується як прихований bridge для інших запитів.

Галочка «Використовувати Oracle hint PARALLEL(8)» додає до основного SELECT:

```sql
SELECT /*+ PARALLEL(8) */
```

Без галочки hint не генерується.

### Готові фільтри категорій ЗО

Для робочої T6 (`kat_zo`) та сирої T6 (`aped46_zo`) доступні швидкі кнопки:

- «Військові» — категорія входить до `31, 50–63, 67, 68, 73, 74` згідно з наданим переліком;
- «Цивільні» — категорія не входить до цього переліку;
- «Особи з інвалідністю» — категорія входить до `2, 28, 30, 32, 36, 39, 41, 45, 49, 66, 78, 79, 80`.

Фільтри додаються як звичайні редаговані умови. Оператор `NOT IN` проходить ту саму перевірку числових значень, що й `IN`.

Перед приєднанням картки дедуплікуються через `ROW_NUMBER()` за ключем зіставлення. Першою береться остання картка за `modify_dt DESC NULLS LAST`, потім за `ip_id DESC`.

### APE 4-6 і APE 4-5

Пряме приєднання сирих періодів може розмножувати рядки APE 4-6. Тому APE 4-5 спочатку агрегується в CTE до зерна:

```text
пакет + РНОКПП
```

У CTE обчислюються мінімальний початок, максимальний кінець і кількість періодів. Після цього виконується складений `JOIN` за пакетом та РНОКПП.

## Правила сирої Т6

Коли одночасно вибрані `sm_packlabel` і `sm_ape4_6data`, генератор автоматично додає:

```sql
plb.slb_fixed = 'Y'
AND plb.slb_actuality = 'Y'
AND plb.slb_st = 'O'
AND pd.aped46_st = 'O'
```

Сторнування фонду оплати виконується так:

```sql
CASE
    WHEN pd.aped46_pay_tp IN (3, 5, 7, 9, 12)
    THEN -ABS(pd.aped46_sum)
    ELSE pd.aped46_sum
END
```

Рік і місяць однаково визначаються в `SELECT`, `WHERE` та `GROUP BY`:

```sql
NVL(pd.aped46_year, plb.slb_charg_year)
NVL(pd.aped46_mnth, plb.slb_charg_mnth)
```

## Готові показники

| Назва в UI | SQL-семантика |
|---|---|
| Фонд оплати | `SUM(sum_narah)` |
| Внески ЄСВ | `SUM(sum_narah_vnes)` |
| Кількість осіб | `COUNT(DISTINCT kod_zo)` |
| Кількість страхувальників | `COUNT(DISTINCT edrpou)` |
| Кількість рядків | `COUNT(*)` |
| Фонд оплати сирої Т6 | `SUM(CASE ... -ABS(aped46_sum) ... END)` |

`COUNT(*)` у проєкті не називається кількістю осіб. Середня зарплата поки не додана, оскільки `AVG(sum_narah)` без попереднього приведення до зерна «особа–місяць» дає семантично ненадійний результат.

## SQL-шаблони

Шаблони знаходяться на шостому кроці застосунку. Кнопка «Вставити» показує SQL у правій панелі, а «Копіювати» одразу копіює його в буфер обміну.

### `t6_edrpou`

Створює `t6_2026_edrpou` із сирої форми Т6.

Використовує:

- `sm_packlabel`;
- `sm_ape4_6data`;
- `mrdorg`;
- `pinsur_main`;
- `pinsur_chng_doc`;
- `pinsur_ankt_a`.

Шаблон формує регіон, страхувальника, ЄДРПОУ, назву організації, РНОКПП, дату народження, суми, місяць, рік, категорію ЗО та стать. Для сум застосовується сторнування, для року й місяця — `NVL`. Діапазони років і місяців беруться з налаштувань над картками шаблонів. Там само можна вибрати OTK: будь-яке значення, основне місце роботи (`1`) або не основне (`0`).

Діапазони років і місяців беруться зі спільних налаштувань шаблонів. Після CTAS шаблон виконує:

SELECT * FROM t1_2024;

## Валідація SQL

Генератор перевіряє:

- формат чисел;
- календарну коректність дат `YYYY-MM-DD`;
- обидві межі `BETWEEN`;
- порожні значення;
- списки `IN`;
- сумісність текстового пошуку з типом колонки;
- Oracle identifier для CTAS;
- унікальність технічних аліасів без урахування регістру;
- заборону `SELECT *` у CTAS із кількома джерелами.

Пошук без урахування регістру генерується симетрично:

```sql
UPPER(column_name) LIKE UPPER('%значення%')
```

У режимі перезапису UI окремо попереджає, що `DROP TABLE ... PURGE` безповоротно видалить поточну таблицю.

## Автоматичні тести

Запуск із PowerShell:

```powershell
powershell -ExecutionPolicy Bypass -File tests\run-tests.ps1
```

Тести працюють у headless Google Chrome без Node.js і зовнішніх бібліотек.

Перевіряються 41 сценарій, зокрема:

2. три таблиці з проміжним зв’язком;
3. непов’язана таблиця;
4. складений JOIN APE 4-6 ↔ APE 4-5;
5. альтернативне зіставлення особи за РНОКПП або паспортом;
6. `COUNT(DISTINCT)` осіб;
7. сторнування;
8. фільтр за датою;
9. `LIKE` без регістру;
10. CTAS із дубльованими аліасами.
11. bridge-маршрути від пакета або робочої T6 до анкет і КВЕД;
12. відсутність вигаданих прямих JOIN;
13. стабільність SQL при зворотному порядку endpoints;
14. унікальність таблиць у `FROM/JOIN`;
15. opt-in фільтри актуального профілю;
16. розділення history route та current document pointer;
17. попередження про розмноження сум.

Перед змінами генератора слід запустити тести, після змін — запустити їх повторно та перевірити `git diff --check`.

## Дані, які ще потрібно перевірити

Не можна вгадувати типи або бізнес-семантику таких полів:

- `APED45_START_DT`;
- `APED45_STOP_DT`;
- `PASS_DT`;
- `PT_NAME`;

Перед використанням потрібні результати `ALL_TAB_COLUMNS`, документація моделі та кілька знеособлених прикладів записів. У схемі неперевірені типи позначені як `UNKNOWN`.
